# File format

Timeline schedules are saved as a single plain JSON file, no binary framing, no compression. This
document describes that format for anyone building an external tool or writing an AI agent that
reads or writes it directly — the app doesn't require you to go through it, so it needs to be
followed exactly.

It's generated by `serialize()` and parsed by `loadFromText()` in `timeline-schedule-tool.html`;
that's the authoritative source if this document and the code ever disagree.

## Top-level shape

```json
{
  "meta": { "name": "My Project", "created": "2026-01-01T09:00:00.000Z", "modified": "2026-01-02T14:30:00.000Z" },
  "holidays": ["2026-12-25", "2026-12-26"],
  "tasks": [ /* Task objects, see below */ ]
}
```

| Field | Type | Notes |
|---|---|---|
| `meta.name` | string | Display name. Missing/empty falls back to `"Untitled Schedule"` on load. |
| `meta.created` | string \| null | ISO 8601 datetime. Set automatically on first save if not already present — don't need to set it when generating a file from scratch. |
| `meta.modified` | string \| null | ISO 8601 datetime. Overwritten on every save; not meaningful to set by hand. |
| `holidays` | string[] | Non-working dates, each `"YYYY-MM-DD"`. Applies globally to every task's scheduling, on top of weekends. Missing/non-array becomes `[]` on load. |
| `tasks` | Task[] | See below. Missing or not an array is treated as an invalid file and rejected outright (the one field this format actually requires). |

## Task object

```json
{
  "id": "t4ns0pm8",
  "name": "Design review",
  "description": "",
  "notes": "",
  "resources": ["Alice", "Bob"],
  "duration": 3,
  "start": "2026-08-24",
  "end": "2026-08-26",
  "manualEnd": false,
  "percentComplete": 40,
  "status": "amber",
  "predecessors": [{ "id": "t1a2b3c4", "lag": 1 }],
  "parentId": null,
  "collapsed": false,
  "tags": ["PO"]
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | string | Unique within the file. Any string works; the app generates `"t" + 7 random base-36 chars`. Referenced by other tasks' `predecessors[].id` and `parentId` — nothing else in the file points at a task any other way. |
| `name` | string | Missing/null becomes `"Untitled task"` on load. Empty string is left as-is (not replaced). |
| `description` | string | Freeform. Defaults to `""`. |
| `notes` | string | Freeform, shown in a separate Notes popover from `description`. Defaults to `""`. |
| `resources` | string[] | People/resource names as free text, no separate resource registry — the same spelling anywhere is treated as the same resource. Also accepts a single comma-separated string on load (split and trimmed) for convenience; always written back out as an array. |
| `duration` | number | Working days, **not calendar days**. `0` is the milestone convention (see below) — not "no duration set" or an error. Negative values and non-numbers are clamped/defaulted to `1` on load. |
| `start` | string | `"YYYY-MM-DD"`. Missing defaults to today's date on load. For a task with children, this is overwritten by the parent-rollup pass in `recalcAll()` regardless of what's in the file (see "Parent/summary tasks" below) — write it if you like, but don't expect it to stick for a parent. |
| `end` | string \| null | `"YYYY-MM-DD"`. For a leaf task, this is normally *derived* from `start` + `duration` (working-day arithmetic, skipping weekends/holidays) rather than read from the file — see `manualEnd` below for the one case where the file's value is authoritative. |
| `manualEnd` | boolean | `false` (default): `end` is computed from `start` + `duration`; whatever's in the file for `end` is ignored and overwritten. `true`: the file's `end` is authoritative instead, and `duration` is derived from it (`end` and `start` together determine the working-day count). Only meaningful for leaf tasks — see below. |
| `percentComplete` | number | `0`–100, clamped on load. For a milestone, only `0` or `100` are meaningful in the UI (an in-between value can be stored but the app only ever writes 0 or 100 for milestones). |
| `status` | `"green"` \| `"amber"` \| `"red"` \| `null` | RAG status. Any other value (including omitting the field) becomes `null` ("not set") on load — there's no separate "invalid" state. |
| `predecessors` | `{id: string, lag: number}[]` | Dependencies. `id` must match another task's `id` in the same file. `lag` is signed working days the successor waits after the predecessor's `end` before it's eligible to start (negative = lead time, the successor can start *before* the predecessor fully finishes). **Legacy shape still accepted on load**: an array of plain id strings (`["t1a2b3c4"]`, no lag) from before this field existed — each is upgraded to `{id, lag: 0}`, reproducing the old "start the next working day" behavior exactly. New files should always use the object form. A task that's its own ancestor's dependent (a cycle) isn't rejected by the loader itself — the app's dependency picker prevents creating one interactively, but a hand-authored file with a cycle in it isn't validated against that. |
| `parentId` | string \| null | The containing task's `id`, or `null` for a top-level task. Defines the hierarchy — there's no separate tree/nesting structure in the file, it's flat with parent pointers. |
| `collapsed` | boolean | Whether this task's children are hidden in the Task List and Gantt views. Only meaningful if the task actually has children (i.e. is some other task's `parentId`); harmless but meaningless otherwise. Defaults to `false`. |
| `tags` | string[] | Freeform labels for filtering/reporting (e.g. `"PO"`, `"DOC"`), no separate tag registry — same "spelling is identity" precedent as `resources`, matched case-insensitively on load and whenever a new one is typed in the app (so `"PO"` and `"po"` collapse to one tag rather than forking). **Unlike `resources`, does not roll up to parent tasks** and works identically on every task type (leaf, parent, milestone) — there's no computed/derived value being protected the way there is for a parent's dates/resources, so nothing about a task's `tags` is ever overwritten by `recalcAll()` beyond that case-canonicalization pass. Defaults to `[]`. |

### The milestone convention

There's no separate `"type": "milestone"` field. A task is a milestone purely because
`duration === 0` (`isMilestone(t)` in the code is exactly that check, nothing more). A milestone's
`end` always equals its `start` — it has no span. Set `duration: 0` and it's a milestone; anything
else and it's a regular task or a parent.

### Parent/summary tasks

Any task that's another task's `parentId` is treated as a **parent** (summary) task, computed, not
directly editable through the normal UI fields:

- `start` = the earliest `start` among its children (recursively).
- `end` = the latest `end` among its children (recursively).
- `duration` is not independently meaningful for a parent — it's not recomputed to match the
  start/end span, and isn't read from the file for scheduling purposes either.
- `resources` = the union of its children's `resources` (deduplicated).
- `percentComplete` = a weighted average across its children's own `duration` and completion.
- `tags` is the one field that's **not** rolled up or otherwise touched by this — a parent's own
  `tags` (if any) stay exactly as set, independent of whatever its children are tagged with.

All of the above happens in `recalcAll()`, on every load and on every edit. If you hand-author a
parent task with different values already in the file, expect them to be silently replaced the
first time the file is loaded or the app recalculates.

### Dependency scheduling

For a leaf task with one or more `predecessors`, its earliest eligible `start` is computed from the
latest of `(predecessor.end + lag working days)` across every predecessor — again, this overwrites
whatever `start` is in the file, unless the task also has no predecessors, in which case the file's
own `start` is authoritative.

## Full example

A minimal but complete two-task schedule with one dependency:

```json
{
  "meta": { "name": "Example", "created": "2026-08-01T00:00:00.000Z", "modified": "2026-08-01T00:00:00.000Z" },
  "holidays": [],
  "tasks": [
    {
      "id": "design",
      "name": "Design",
      "description": "",
      "notes": "",
      "resources": ["Alice"],
      "duration": 4,
      "start": "2026-08-24",
      "end": "2026-08-27",
      "manualEnd": false,
      "percentComplete": 100,
      "status": "green",
      "predecessors": [],
      "parentId": null,
      "collapsed": false,
      "tags": ["DOC"]
    },
    {
      "id": "build",
      "name": "Build",
      "description": "",
      "notes": "",
      "resources": ["Bob"],
      "duration": 6,
      "start": "2026-08-28",
      "end": "2026-09-04",
      "manualEnd": false,
      "percentComplete": 0,
      "status": null,
      "predecessors": [{ "id": "design", "lag": 0 }],
      "parentId": null,
      "collapsed": false,
      "tags": ["PO"]
    }
  ]
}
```

## Forward/backward compatibility

Every task is passed through `normalizeTask()` on load, which fills in a sensible default for any
missing or malformed field — this is what lets old files (missing fields added in later versions,
like `status` or `collapsed`) keep loading correctly, and what makes hand-authoring a minimal file
safe (you don't have to specify every field). The reverse isn't true: `normalizeTask()` returns a
new object literal listing only the fields above, so any field on a task that isn't in this document
is silently dropped the first time the file is loaded and re-saved. Don't rely on round-tripping
custom fields through the app.
